# ApexDecision System & Benchmark Audit Report

**Date:** September 20, 2026  
**Auditor:** ApexDecision Engineering & Verification  
**Repository Target:** `apex_decision`  
**Purpose:** Technical and statistical audit of the pre-existing ApexDecision system, model architecture, training configuration, calibration layer, and the validity of the previously reported 100.0% benchmark score.

---

## Executive Summary

A thorough examination of `apex_decision` reveals that while the technical implementation of ModernBERT with LoRA parameter-efficient fine-tuning and mixed-precision inference executes efficiently on the target RTX 2050 GPU, **the previously reported 100.0% accuracy score on the 150-sample "Hard Adversarial Intelligence Suite" is statistically and scientifically invalid**.

The 100.0% result was the direct artifact of severe template duplication and data leakage across splits: 1,000 synthetic examples were generated by cycling through only 25 negation templates, 8 distraction scenarios, 8 policy rules, and 16 triage templates, which were then randomly shuffled into train (700), validation (150), and test (150) splits. As a consequence, the exact same logical statements and assertions appeared in both the training set and the test set with only minor surface token variations (e.g. changing an AWS region or randomized ticket ID). The model was evaluated on memorized patterns rather than generalized reasoning.

Claiming that ApexDecision "beats TypeSafe Jev (67.8%)" based on this evaluation is unfounded. The 67.8% Jev figure corresponds to a completely different, published workflow evaluation rather than Jev's 96.3% published grounding benchmark. 

Below is the exhaustive 15-point audit of the system.

---

## Detailed 15-Point System Audit

### 1. Backbone Architecture
* **Backbone Model:** `answerdotai/ModernBERT-base` (Hugging Face / PyTorch).
* **Architecture Details:** Bidirectional transformer encoder with 22 hidden layers, hidden dimension $D = 768$, intermediate feed-forward dimension $d_{ff} = 1152$, 12 attention heads, vocabulary size of 50,368 tokens, Rotary Position Embeddings (RoPE), and GeLU activations.
* **Input Pooling:** Attention-masked mean pooling (`MeanPooler`) over token representations.

### 2. Parameter Count
* **Total Parameters:** **151,319,818** (~151.32M).
  * Base ModernBERT Backbone: **149,014,272** (~149.01M).
  * LoRA Adapters: **2,297,856** (~2.30M).
  * Task Readout Heads:
    * `binary_head`: Linear(768, 1) $\rightarrow$ 769 parameters (768 weight + 1 bias).
    * `categorical_head`: Linear(768, 8) $\rightarrow$ 6,152 parameters (when `num_classes=8`).
    * `ordinal_head`: Linear(768, 5) $\rightarrow$ 3,845 parameters (`num_levels=5`).
    * Total Head Parameters: **7,690** (or **10,765** including all heads simultaneously).

### 3. Frozen Parameters
* **Frozen Count:** **149,014,272** parameters (98.48% of the model).
* **Details:** When `use_lora=True` is enabled, all native parameters of the `ModernBERT-base` backbone (token embeddings, all 22 self-attention blocks, feed-forward layers, layer normalizations) have `requires_grad = False`.

### 4. Actually Trained Parameters
* **Trainable Count:** **2,305,546** parameters (1.52% of total parameters).
* **Details:** During fine-tuning in `benchmarks/train_lora.py`, only the newly allocated PEFT LoRA projection matrices and the downstream classification heads are optimized by `torch.optim.AdamW`.

### 5. LoRA Modules Trained
* **PEFT Configuration:**
  * Rank: $r = 16$
  * Alpha: $\alpha = 32$ ($\text{scaling} = 2.0$)
  * Dropout: 0.05
  * Bias: None
  * Target Modules: Attention projections `["Wqkv", "Wo", "q_proj", "k_proj", "v_proj", "out_proj"]` across all 22 layers. Total LoRA parameter count: **2,297,856**.

### 6. Training Dataset Size
* **In `intelligence_suite.json`:** Exactly **700 samples** (first 700 of 1,000 shuffled records).
* **In `run_benchmark.py` (older linear probe):** 200 samples selected from `complex_binary_data.json`.

### 7. Validation Dataset Size
* **In `intelligence_suite.json`:** Exactly **150 samples** (indices 700 to 849).
* **In `run_benchmark.py`:** 50 samples.

### 8. Test Dataset Size
* **In `intelligence_suite.json`:** Exactly **150 samples** (indices 850 to 999).
* **In `run_benchmark.py`:** 50 samples.

### 9. Semantic Overlap Across Splits (Train / Validation / Test)
* **Finding:** **Severe, pervasive semantic overlap and data leakage.**
* **Root Cause Analysis:** Inspecting `benchmarks/generate_intelligence_suite.py`:
  * *Complex Negation category (250 samples):* Constructed by cycling through only **25 hardcoded template pairs** (`templates[idx % len(templates)]`). The 25 template pairs were duplicated 10 times each across the dataset, altering only random service names (e.g., `AuthService` vs `VaultManager`) and incident IDs.
  * *Adversarial Distraction category (250 samples):* Sampled with replacement from only **8 fixed scenarios**.
  * *NLI Policy category (250 samples):* Sampled with replacement from only **8 fixed policy statements**.
  * *High-Cardinality Triage category (250 samples):* Sampled from only **16 fixed ticket templates**.
  * The resulting 1,000 samples were randomly shuffled and partitioned into 700 train / 150 val / 150 test. As a result, virtually every premise and assertion in the test set had multiple identical semantic copies in the training set.

### 10. Synthetic Nature of Benchmark
* **Finding:** **100% synthetic.**
* Every example in `intelligence_suite.json` was generated programmatically from template strings defined in Python scripts.

### 11. Generation Method for Benchmark Labels
* **Finding:** **Generated via hardcoded template rules.**
* Ground-truth labels were hardcoded directly in Python tuple literals (e.g., `(premise, assertion, False, "subtle_conjunction_failure")`).

### 12. Independence of Benchmark Examples
* **Finding:** **NOT independent.**
* The test examples are not independent draws from an out-of-distribution or held-out domain; they are near-identical lexical perturbations of the training samples.

### 13. Calibration Data Overlap with Test Set
* **Finding:** While `train_lora.py` fitted `TemperatureScaler` on the 150 validation samples and evaluated on the 150 test samples, the underlying distributions were identical due to template sharing. Consequently, the calibration set was effectively identical to the test set.

### 14. Validity of Reported ECE on Held-Out Data
* **Finding:** **Invalid.**
* `benchmark_results.json` reports `hard_test_ece: 0.0`. This occurred because the model achieved 100.0% accuracy with high uncalibrated confidence on memorized templates. When accuracy is 1.0 and predicted probability is $\approx 1.0$ in the top confidence bin, $|acc - conf| \approx 0.0$. This does not reflect real-world calibration on unseen data.

### 15. Statistical Meaning of the 100% Accuracy Claim
* **Finding:** **Statistically uninformative and scientifically invalid.**
* A score of 150/150 on a test set contaminated with training templates proves only that the LoRA adapter possesses sufficient capacity (2.3M parameters) to memorize 57 unique template structures.
* The 95% Wilson score binomial confidence interval for 150/150 is $[97.53\%, 100.0\%]$, but this calculation relies on the assumption of independent and identically distributed (i.i.d.) test samples. Because that assumption is violated, the confidence interval is invalid.
* Crucially, the 100% result provides zero evidence that ApexDecision can generalize to real-world grounding, detect subtle factual contradictions in un-templated text, or outperform TypeSafe Jev's published 96.3% accuracy on 108 grounding claims.

## Action Items for Next-Generation Grounding Benchmark

1. **Abandon generic text classification** and transition to a true **grounding verifier** evaluating `(source, claim) -> {SUPPORTED, NOT_SUPPORTED}`.
2. **Build a leak-free 5,000+ example benchmark** across 8 distinct domains with 20 documented adversarial failure modes.
3. **Enforce source-level disjoint partitioning**: No source document or premise appearing in the test set may appear in the training, validation, or calibration splits.
4. **Implement an isolated 108-claim Jev-style evaluation suite** across 6 domains with 4 difficulty tiers, strictly reserved for reporting without any training exposure.
5. **Fit calibration strictly on a dedicated calibration split** and report true out-of-domain ECE on the untouched test set.
